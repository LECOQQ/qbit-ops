# qbit-ops demo environment

Two disposable, synthetic qBittorrent instances for taking safe
screenshots and terminal recordings of the qbit-ops TUI. No real
qBittorrent instance, private tracker, or downloaded media is ever
involved.

The qbit-ops TUI only ever points at the first instance (the
"seeder"). The second ("leecher") exists purely to give the seeder a
real peer to transfer with, so the Overview's rate graph has actual
bytes/s to plot instead of a flat line.

## Prerequisites

- Docker with the `compose` plugin
- Poetry (`make install` already sets up the project)
- [VHS](https://github.com/charmbracelet/vhs) -- optional, only for `make demo-record`

## Usage

```bash
make demo-up       # generate fixtures, start both qBittorrent instances, seed and pair them
make demo-tui       # restart the live transfer, then launch the TUI against the seeder only
make demo-record    # restart the live transfer, then record demo/tui.tape with VHS
make demo-transfer  # restart the live transfer on its own, without launching anything
make demo-reset     # wipe and recreate the exact same demo inventory
make demo-down      # stop and remove all demo containers, network, state
```

## Isolation

- WebUIs bound to `127.0.0.1:18080` (seeder) and `127.0.0.1:18081`
  (leecher) only, never a LAN-reachable address.
- `qbit-ops` is pointed at `demo/qbit-ops.env` explicitly (`QBIT_OPS_ENV_FILE`) --
  the repository `.env` and `~/.config/qbit-ops/.env` are never read. It
  only ever talks to the seeder; the leecher's WebUI is not consumed by
  the application at all.
- Fixed demo-only credentials (`demo` / `demo-only`); no real qBittorrent
  instance, private tracker, or passkey is ever contacted.
- DHT, PeX, LSD, and UPnP/NAT-PMP are disabled on both instances from
  first boot, so neither ever discovers or is discovered by a real,
  Internet-facing peer. The one exception is deliberate and explicit:
  `demo/arm_transfer.py` hands the leecher the seeder's private Docker
  network address directly (via `torrents_add_peers`) for exactly one
  fixture, so the two disposable containers transfer with each other.
  This is not peer discovery -- it never leaves the Docker network the
  two containers share, and no other fixture is ever paired this way.
- That one transfer is rate-limited to 100 kB/s on the leecher's
  download, so it draws a readable ~30s ramp instead of finishing
  before a recording can start.
- The Docker network itself still permits outbound egress -- only
  qBittorrent's own peer-discovery features are turned off.
- All 16 torrents are synthetic and built from locally generated bytes
  -- nothing is downloaded from the Internet. Their announce URLs are
  RFC 2606 reserved names, never a real tracker: `tracker-primary.example`
  and `tracker-mirror.example` resolve to a third, disposable container
  (`tracker` in `compose.yml`) running the same stdlib-only tracker
  service `tests/integration` uses for its own tests -- bind-mounted
  read-only, never copied, never published to the host.
  `tracker-error.example` resolves to that same container on a path it
  404s on, so it demonstrably answers with an error rather than being
  merely unreachable. `tracker-dead.invalid` resolves nowhere at all.

## Recording output

`make demo-record` writes `demo/output/qbit-ops-demo.gif` (gitignored).
Review it before publishing -- it is not copied into the README automatically.

## Troubleshooting

- **`make demo-up` hangs waiting for the WebUI**: check `docker logs qbit-ops-demo`
  or `docker logs qbit-ops-demo-leecher`.
- **Stale state after edits to `fixtures.toml`**: run `make demo-reset`.
- **The Overview graph is flat**: `make demo-tui` and `make demo-record` both
  restart the transfer before launching anything, but if the leecher container
  isn't running (`make demo-up` was never called, or crashed) `demo-transfer`
  fails loudly instead of silently doing nothing.
- **`make demo-record` fails with "vhs not found"**: install VHS separately;
  it is never a Python dependency of this project.
- **The Trackers page looks wrong**: check `docker logs qbit-ops-demo-tracker`
  for the `.example` hosts. `tracker-dead.invalid` is *supposed* to show
  critical/unreachable -- it never resolves, by design.
