# qbit-ops demo environment

Three disposable containers for taking safe screenshots and terminal
recordings of the qbit-ops TUI: two synthetic qBittorrent instances and
a tracker. No real qBittorrent instance, private tracker, or downloaded
media is ever involved.

The TUI only ever points at the first instance (the "seeder"). The
second ("leecher") exists purely to give the seeder a real peer to
transfer with, so the Overview's rate graph has actual bytes/s to plot
instead of a flat line. The third answers the fixtures' announce URLs,
so the Trackers page has a list rather than nothing.

## Prerequisites

- Docker with the `compose` plugin
- Poetry (`make install` already sets up the project)
- [VHS](https://github.com/charmbracelet/vhs) -- optional, only for `make demo-record`
- `beautify` -- optional, only for `make demo-beautify`; it is a separate
  local tool, and the target says where to install it from if it is missing

## Usage

```bash
make demo-up        # generate fixtures, start all three containers, seed and pair them
make demo-tui       # restart the live transfer, then launch the TUI against the seeder only
make demo-record    # restart the live transfer, then record both tapes with VHS
make demo-beautify  # compose the recorded captures onto backgrounds for the README
make demo-transfer  # restart the live transfer on its own, without launching anything
make demo-reset     # wipe and recreate the exact same demo inventory
make demo-down      # stop and remove all demo containers, network, state
make demo-doctor    # check that docker, compose and poetry are present
```

## Isolation

- WebUIs bound to `127.0.0.1:18080` (seeder) and `127.0.0.1:18081`
  (leecher) only, never a LAN-reachable address. The tracker publishes
  no port at all -- it is reachable only from the Docker network.
- `qbit-ops` is pointed at `demo/qbit-ops.env` explicitly (`QBIT_OPS_ENV_FILE`) --
  the repository `.env` and `~/.config/qbit-ops/.env` are never read. It
  only ever talks to the seeder; the leecher's WebUI is not consumed by
  the application at all.
- Fixed demo-only credentials (`demo` / `demo-only`); no real qBittorrent
  instance, private tracker, or passkey is ever contacted.
- DHT, PeX, LSD, and UPnP/NAT-PMP are disabled on both instances from
  first boot, so neither ever discovers or is discovered by a real,
  Internet-facing peer. The one exception is deliberate and explicit:
  `demo/arm_transfer.py` hands the leecher the seeder's private Docker
  network address directly (via `torrents_add_peers`) for exactly one
  fixture, so the two disposable containers transfer with each other.
  This is not peer discovery -- it never leaves the Docker network the
  two containers share, and no other fixture is ever paired this way.
- That one transfer is rate-limited to 100 kB/s on the leecher's
  download, so it draws a readable ~30s ramp instead of finishing
  before a recording can start.
- The Docker network itself still permits outbound egress -- only
  qBittorrent's own peer-discovery features are turned off.
- All 16 torrents are synthetic and built from locally generated bytes;
  nothing is downloaded from the Internet. Their announce URL sits
  outside the bencoded `info` dict, so adding one leaves every infohash
  unchanged.

## Trackers

Every announce URL is an RFC 2606 reserved name, never a real tracker.
Three of them resolve to the `tracker` container, which bind-mounts the
stdlib-only service `tests/integration` already uses -- read-only, never
copied. The fourth resolves nowhere.

| Host | Torrents | Answers |
| --- | --- | --- |
| `tracker-primary.example` | 10 | normally |
| `tracker-mirror.example` | 3 | normally |
| `tracker-error.example` | 2 | 404, on a path the service rejects |
| `tracker-dead.invalid` | 1 | never resolves |

The spread is uneven on purpose: the Trackers page is worth showing when
it ranks, and the two failing hosts fail differently, so `trackers
status` reports an error distinct from a non-answer.

Two consequences worth knowing before reading a capture. qBittorrent
announces on a delay, so give `make demo-up` a moment before recording.
And a paused torrent never announces at all, so the endpoints attached
to one stay `warning` ("not contacted") forever -- real behaviour, not
an artefact.

## Recording output

<!-- doc-links: ignore-next-line -->
Everything lands in `demo/output/`, which is gitignored and therefore
absent from a fresh checkout until something records into it. Nothing is
copied into the repository README automatically; review it first.

```
make demo-record    demo/output/qbit-ops-demo.gif   the hero, from demo/tui.tape
                    demo/output/*.png               six stills, from demo/shots.tape
make demo-beautify  demo/output/*.webp              the stills, framed and tinted
                    demo/output/qbit-ops-hero.gif   the hero, same treatment
```

The two tapes are split because their constraints are opposite: a still
is read, so it can be wide and slow; the hero GIF is watched, so every
frame is paid for.

## Troubleshooting

- **`make demo-up` hangs waiting for the WebUI**: check `docker logs qbit-ops-demo`
  or `docker logs qbit-ops-demo-leecher`.
- **Stale state after edits to `fixtures.toml`**: run `make demo-reset`.
- **The Overview graph is flat**: `make demo-tui` and `make demo-record` both
  restart the transfer before launching anything, but if the leecher container
  isn't running (`make demo-up` was never called, or crashed) `demo-transfer`
  fails loudly instead of silently doing nothing.
- **`make demo-record` fails with "vhs not found"**: install VHS separately;
  it is never a Python dependency of this project.
- **The Trackers page looks wrong**: check `docker logs qbit-ops-demo-tracker`.
  `tracker-dead.invalid` is *supposed* to show critical/unreachable.
- **The wordmark renders small**: the full mark needs a 58-column identity
  column, which lands around 140 terminal columns. Both tapes set a width
  that clears it; a hand-run terminal may not.
